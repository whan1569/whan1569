## 🧭 성장 흐름

저는 개발을 단순한 기술 스택의 나열이 아니라, 시대에 따라 요구되는 문제 해결 방식의 확장으로 이해해왔습니다.

초중고 시절에는 알고리즘과 자료구조를 공부하며 문제를 작은 단위로 분해하는 기본기를 익혔습니다.
다익스트라 알고리즘 같은 경로 탐색 로직을 직접 구현하며, 복잡한 문제도 적절한 구조로 나누면 계산 가능한 형태로 바꿀 수 있다는 감각을 얻었습니다.

대학에서는 프레임워크와 객체지향을 배우며, 단순 알고리즘 구현을 넘어 프로그램을 구조화하고 표현하는 방법을 익혔습니다.
졸업 이후에는 혼자 학습하며 운영, 배포, 관리의 중요성을 공부했고, 작성한 프로그램이 실제 사용자에게 제공되기 위해 필요한 흐름을 이해하려 했습니다.

회사에서는 실제 장비와 시스템을 직접 연동하고, 디버깅하고, 문제를 파악하고, 그 과정을 문서화하며 협업하는 경험을 쌓았습니다.
개인 프로젝트와 데이터 공부를 통해서는 데이터를 수집하고 정제하고 시각화하며, 복잡한 현실 정보를 사람이 이해할 수 있는 형태로 표현하는 연습을 꾸준히 해왔습니다.

```text
기초 알고리즘과 작은 모듈 이해
→ 객체지향과 프레임워크를 통한 프로그램 구조화
→ 실제 개발을 통한 아이디어 구현
→ 배포와 운영을 통한 서비스화
→ 회사에서의 연동, 디버깅, 문제 파악, 문서화, 협업
→ 데이터 정제와 시각화를 통한 인사이트 표현
→ 한계와 실패까지 기록으로 남기는 개발 태도
```

## 📌 Positioning

저는 개발을 완성된 결과물만으로 보지 않습니다.
문제를 마주하고, 직접 구현해보고, 한계에 부딪히고, 다시 방향을 수정하는 과정까지 개발자의 경험이라고 생각합니다.

지금까지의 프로젝트 중에는 명확한 결실을 맺은 것도 있고, 기술적 가능성은 확인했지만 비용과 효율 문제로 중단한 것도 있으며, 아이디어는 좋았지만 당시의 역량과 시간 안에서 끝까지 구현하지 못한 것도 있습니다.
하지만 그 과정들은 레포지토리와 문서에 흔적으로 남아 있고, 저는 그 흔적들이 제가 실제로 얼마나 많은 문제를 마주하고 시도해왔는지를 보여준다고 생각합니다.

저는 개발자를 단순히 코드를 작성하는 사람이 아니라,
현실의 문제를 이해하고, 구조화하고, 구현하고, 운영하며, 다시 데이터와 문서로 표현하는 사람이라고 생각합니다.

제가 걸어온 흐름은 기초 알고리즘에서 시작해 객체지향과 프레임워크, 배포와 운영, 실제 회사의 연동과 디버깅, 그리고 데이터 정제와 시각화로 이어졌습니다.

그래서 제가 다루는 문제는 다음과 같습니다.

* 작은 문제를 알고리즘과 자료구조로 분해하기
* 아이디어를 객체와 모듈로 구조화하기
* 구조화된 프로그램을 실제 동작하는 서비스로 구현하기
* 프로그램을 배포하고 운영 가능한 형태로 만들기
* 실제 회사 환경에서 발생하는 문제를 연동, 디버깅, 문서화로 해결하기
* 복잡한 데이터를 정제하고 시각화하여 인사이트로 표현하기
* 완성하지 못한 시도에서도 한계와 판단 근거를 기록으로 남기기

제 강점은 모든 프로젝트를 완벽히 성공시킨 것이 아니라,
다양한 문제를 직접 시도해보고 어디서 막히는지, 무엇이 비용 대비 맞지 않는지, 어떤 구조가 실제 환경에서 어려운지를 경험으로 축적했다는 점입니다.

저는 문제를 **계산 가능한 구조 → 동작하는 프로그램 → 운영 가능한 서비스 → 공유 가능한 문서와 데이터**로 바꾸는 흐름을 이해하려고 해왔고, 그 과정에서 성공과 실패를 모두 기록으로 남겨왔습니다.

## 🧭 개발 관점

알고리즘은 문제를 계산 가능한 형태로 바꾸는 훈련이었습니다.
객체지향과 프레임워크는 프로그램을 유지 가능한 구조로 표현하는 훈련이었습니다.
배포와 운영은 코드가 실제 사용자에게 닿기 위한 조건을 이해하는 과정이었습니다.
회사에서의 디버깅과 문서화는 다른 사람의 문제와 요구를 기술적으로 해석하고 해결하는 과정이었습니다.
데이터 정제와 시각화는 복잡한 현실에서 의미 있는 신호를 뽑아내고 전달하는 연습이었습니다.

저는 기술을 많이 나열하는 것보다,
현실의 문제를 기술로 번역하고 다시 사람이 이해할 수 있는 형태로 표현하는 것을 중요하게 생각합니다.

## 🧭 Working Principles

* 완성된 결과만큼, 왜 막혔는지와 왜 중단했는지도 중요하게 기록한다.
* 기술적 가능성과 실제 구현 가치가 항상 같지는 않다고 본다.
* 작은 로직을 이해한 뒤, 그것을 모듈과 시스템으로 확장한다.
* 프로그램은 구현에서 끝나는 것이 아니라 운영과 전달까지 고려해야 한다.
* 실제 현장의 문제는 코드보다 먼저 상황 파악과 재현이 중요하다.
* 협업에서는 말보다 기록이 오래 남고, 기록이 문제 해결의 기준이 된다.
* 데이터는 그대로 의미가 있는 것이 아니라, 정제되고 표현될 때 가치가 생긴다.
* 실패한 프로젝트도 남은 흔적이 있다면 다음 판단의 재료가 된다.
